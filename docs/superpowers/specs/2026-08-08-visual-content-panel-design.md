# Визуальная панель управления портфолио

Дата: 2026-08-08  
Статус: согласовано устно, ожидает финальной проверки владельцем

## Цель

Перестроить портфолио так, чтобы владелец мог через визуальную панель создавать, редактировать, упорядочивать, скрывать и удалять проекты и обычные страницы. Для повседневного обновления сайта не должно требоваться редактирование кода.

Текущий Windows XP-дизайн, окна, меню «Пуск», рабочий стол и мобильное поведение сохраняются. Работа на этом этапе касается структуры и управления содержимым, а не редизайна.

## Выбранный подход

Использовать Pages CMS как визуальный редактор. Владелец входит в Pages CMS через свой GitHub-аккаунт. Редактор работает с содержимым репозитория `marrorball/portfolio` и сохраняет изменения обратно в GitHub.

На публичном сайте не будет формы входа, токенов или секретов. Право изменять содержимое определяется доступом GitHub-аккаунта к репозиторию. Посетители портфолио видят только опубликованный сайт.

Pages CMS выбран вместо:

- собственного редактора, которому потребовались бы сервер, отдельная авторизация и постоянная поддержка;
- Decap CMS внутри `/admin`, которому на GitHub Pages потребовалась бы отдельная OAuth-инфраструктура.

## Архитектура

Система состоит из четырёх изолированных частей:

1. **Содержимое** — отдельные файлы проектов, страниц, резюме и настроек.
2. **Pages CMS** — визуальные формы, описанные в `.pages.yml`.
3. **Сборка GitHub Pages** — Jekyll собирает опубликованные данные и генерирует индекс содержимого.
4. **Интерфейс портфолио** — HTML-каркас, таблица стилей и JavaScript, который создаёт окна из опубликованных данных.

Предлагаемая структура:

```text
portfolio/
├── .pages.yml
├── _config.yml
├── _projects/
│   └── <project-slug>.md
├── _portfolio_pages/
│   └── <page-slug>.md
├── _data/
│   ├── site.yml
│   └── resume.yml
├── assets/
│   ├── css/site.css
│   ├── js/app.js
│   └── media/
│       ├── projects/<project-slug>/
│       └── pages/<page-slug>/
├── content.json
└── index.html
```

`index.html` остаётся оболочкой Windows XP. Стили и логика выносятся из нынешнего файла в `assets/css/site.css` и `assets/js/app.js`. Встроенные base64-изображения переносятся в `assets/media`.

## Модель содержимого

### Проект

Каждый проект — отдельная запись со следующими полями:

- системный идентификатор из имени файла;
- название;
- категория;
- год;
- статус проекта;
- краткое описание;
- обложка;
- галерея изображений;
- теги;
- необязательная ссылка на Behance;
- порядок отображения;
- флаг `published`;
- произвольный список разделов кейса.

Раздел кейса содержит название вкладки, необязательную иконку и форматируемое содержимое. Владелец может добавлять, удалять и менять местами разделы без изменения шаблона сайта.

### Страница

Каждая обычная страница — отдельная запись со следующими полями:

- системный идентификатор;
- заголовок;
- иконка;
- форматируемое содержимое;
- порядок;
- флаг `published`;
- переключатели показа на рабочем столе и в меню «Пуск».

Так можно добавлять страницы вроде «Обо мне», «Услуги», «Награды» или «Контакты». Для первой версии все пользовательские страницы используют один универсальный шаблон окна. Произвольное визуальное конструирование макета окна в эту задачу не входит.

### Резюме

Резюме хранится как одна структурированная запись:

- опыт работы;
- образование;
- публикации;
- навыки;
- инструменты;
- ссылки и контакты.

Каждый повторяемый блок можно добавлять, удалять и менять местами.

### Настройки сайта

Настройки включают:

- имя и роль владельца;
- контактные данные;
- категории проектов;
- подписи системных пунктов;
- сообщения загрузочного окна;
- порядок основных пунктов рабочего стола и меню «Пуск».

Визуальная тема Windows XP, размеры окон и системное поведение остаются в коде и не выводятся в CMS на первом этапе.

## Работа визуальной панели

В Pages CMS отображаются четыре раздела:

1. «Проекты»;
2. «Страницы»;
3. «Резюме»;
4. «Настройки сайта».

Для проектов и страниц разрешены операции создания, переименования, редактирования и удаления. Изображения загружаются в `assets/media` через медиабиблиотеку. CMS ограничивает загружаемые медиа форматами изображений и формирует безопасные имена файлов.

Скрытие записи выполняется через `published: false`. Такая запись остаётся в GitHub, но не попадает в `content.json` и не отображается на публичном сайте.

## Поток данных и публикация

1. Владелец входит в Pages CMS через GitHub.
2. Pages CMS показывает формы на основе `.pages.yml`.
3. После сохранения Pages CMS создаёт коммит в основной ветке репозитория.
4. GitHub Pages запускает сборку Jekyll.
5. Jekyll читает `_projects`, `_portfolio_pages` и `_data`, исключает неопубликованные записи и создаёт `content.json`.
6. Публичный сайт загружает `content.json` и создаёт рабочий стол, папки, окна, вкладки кейсов и меню.

История Git остаётся резервной копией каждого изменения. Ошибочное редактирование можно вернуть отдельным коммитом без восстановления базы данных.

## Валидация и обработка ошибок

- Обязательные поля проверяются настройками Pages CMS до сохранения.
- Идентификаторы проектов и страниц должны быть уникальными.
- Порядок задаётся целым числом; при одинаковом значении используется алфавитный порядок заголовков.
- Необязательные ссылки и изображения не должны ломать карточку или окно.
- Если `content.json` не загрузился, сайт показывает стилизованное XP-сообщение об ошибке вместо пустого экрана.
- Некорректная отдельная запись пропускается, а остальные опубликованные записи продолжают работать.
- Удаление проекта не удаляет автоматически общие изображения. Перед удалением CMS должна показывать стандартное подтверждение.

Содержимое разделов выводится как форматированный HTML, созданный владельцем через CMS. Доступ к редактированию ограничен GitHub-правами репозитория; произвольный ввод посетителей сайт не принимает.

## Миграция текущего сайта

Миграция выполняется без изменения публичного содержания:

1. Сохранить текущие тексты, порядок проектов и ссылки.
2. Извлечь встроенные изображения из `index.html` в отдельные файлы.
3. Перенести существующие проекты в `_projects`.
4. Перенести «Обо мне», резюме, контакты и системные подписи в управляемые данные.
5. Разделить HTML, CSS и JavaScript.
6. Подключить генерацию `content.json`.
7. Добавить и проверить `.pages.yml`.
8. Сравнить новую локальную версию с опубликованным сайтом на компьютере и телефоне.

## Проверка

Перед публикацией должны пройти:

- сборка Jekyll без ошибок;
- автоматическая проверка обязательных полей, уникальности идентификаторов и существования локальных медиафайлов;
- проверка открытия каждого проекта и каждой вкладки;
- проверка создания, изменения, скрытия и удаления тестовой записи через Pages CMS;
- визуальная проверка основных окон на широком экране и мобильном размере;
- проверка ссылок Email, Telegram и Behance;
- сравнение количества и порядка перенесённых проектов с текущей версией.

Тестовая запись удаляется до финальной публикации.

## Критерии готовности

Работа считается завершённой, когда:

- владелец входит в визуальную панель своим GitHub-аккаунтом;
- посторонний GitHub-аккаунт без доступа к репозиторию не может сохранять изменения;
- проект можно создать, заполнить изображениями, опубликовать, изменить, скрыть и удалить без редактирования кода;
- универсальную страницу можно создать и вывести на рабочий стол или в меню «Пуск»;
- резюме и основные настройки меняются через формы;
- после сохранения GitHub Pages автоматически обновляет сайт;
- текущие проекты, тексты, ссылки и мобильное поведение сохранены;
- Windows XP-интерфейс продолжает работать без ошибок.

## Вне объёма первой версии

- собственная база данных;
- собственная система логинов и паролей;
- доступ редакторов без GitHub;
- drag-and-drop-конструктор произвольного дизайна окон;
- комментарии, аналитика и отправка форм через сервер;
- автоматическое удаление неиспользуемых медиафайлов.
